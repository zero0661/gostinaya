## 1. Что произошло

Основной сайт на Ghost неожиданно стал показывать стандартную тему Casper вместо доработанной Liebling. Пользовательская тема сохранилась и была восстановлена. Смена оформления была внешним признаком несанкционированного управления сайтом.

В серверных журналах за 4 октября обнаружена последовательность запросов с адреса 2.27.132.175: сначала попытки чтения данных через уязвимый Content API, затем операции Admin API с темами и страницами. В Ghost History изменения темы записаны от имени интеграции Zapier. Это указывает на использованную интеграцию, но не означает, что атака совершена компанией Zapier.

До обновления работал Ghost 5.130.6. Известная уязвимость CVE-2026-26980 / GHSA-w52v-v783-gw97 позволяла читать данные базы через SQL injection в Content API, включая секреты API. Официально затронуты версии 3.24.0–6.19.0, исправление выпущено в 6.19.1. Административный ключ позволяет выполнять разрешённые операции через API отдельно от входа пользователя с кодом из письма.

Наиболее обоснованная реконструкция: эксплуатация уязвимости → извлечение Admin API secret → подписанные запросы Admin API → изменение тем и страниц. Журналы показывают запросы, нацеленные на secret из api_keys, и последующие успешные административные операции. Сам извлечённый секрет в распоряжении расследования отсутствует. Полный объём прочитанных данных не установлен.

## 4. Почему не пришёл код входа в Ghost

Запрос к Admin API по интеграционному ключу не является обычным входом staff пользователя в браузере. У него отдельный механизм авторизации; код из письма для каждого такого запроса не требуется.

Следовательно, отсутствие письма с кодом совместимо с атакой через украденный Admin secret. Оно не доказывает взлом почты и не означает, что злоумышленник прошёл обычный вход с паролем. Ротация ключей закрывает доступ через прежние секреты; смена staff паролей и отзыв сеансов закрывают другую группу доступов.

## 7. Резервные копии: подтверждённый результат

Первая копия after-login-20261005T052010Z создана на VPS и проверена на Mac. Вторая after-login-20261005T055924Z создана ежедневным сервисом, скачана LaunchAgent и проверена. Каждая содержит зашифрованный архив около 1,5 GB и четыре сопутствующих файла.

Сервер имеет только публичный RSA ключ. Закрытый private.pem хранится на Mac. Без него расшифровать архив нельзя. SSH download-key — отдельный ключ доступа к выгрузке, не ключ расшифровки.

Шифрование: независимый случайный 64-byte материал; первая половина используется для AES password, вторая — для HMAC. Материал обёрнут RSA-OAEP-SHA256. Архив шифруется AES-256-CBC с PBKDF2, 200000 итераций. HMAC-SHA256 проверяется до расшифровки и охватывает marker формата, wrapped key и ciphertext; SHA256 отдельно проверяет файлы при передаче. Здесь AES-CBC используется совместно с предварительно проверяемым HMAC.

SQL Ghost восстанавливается в изолированную временную базу в ходе каждого создания; SQLite снимается штатным online backup. На Mac выполнены полная расшифровка, gzip и проверки структуры/баз. Полный запуск восстановленного сайта на другом сервере пока не выполнен.

## Что нужно сохранить

Каждая папка копии содержит ровно пять файлов:

- project.tar.gz.enc
- key.enc
- archive.hmac
- SHA256SUMS
- COMPLETE

Для расшифровки обязательно нужен соответствующий закрытый RSA ключ private.pem. Он находится на Mac в ~/AfterLoginBackups/private.pem и прежней папке Documents; на VPS только публичный ключ. Потеря всех копий private.pem делает архивы невосстановимыми. Можно скопировать целую папку зашифрованной копии на съёмный диск; ключ хранить защищённо. Рабочую ~/AfterLoginBackups не переносить без изменения LaunchAgent и путей.

Отдельный SSH download-key разрешает только протокол latest/file через forced command с restrict. Он не является ключом расшифровки. Экспорт доступен только для текущей серверной копии, пяти разрешённых файлов и числового смещения. Произвольные команды запрещены кодом; отдельный production-тест их отказа ещё не выполнен.

## Что проверяется

На сервере: SQLite integrity/foreign keys; восстановление SQL в отдельную временную базу, количество posts/users/settings и CHECK TABLE пяти таблиц; затем удаление тестовой базы. На Mac: SHA256 всех файлов, RSA-OAEP-SHA256, HMAC-SHA256 до расшифровки, AES-256-CBC/PBKDF2 200000, полная gzip-проверка, структура tar, SQL gzip, SQLite integrity/foreign keys. Временные открытые данные удаляются.

Признаки успеха: BACKUP_CREATED_AND_DATABASE_RESTORE_TESTED_OK, DAILY_BACKUP_AND_RETENTION_OK, OFFSITE_BACKUP_DECRYPTION_AND_INTEGRITY_OK, OFFSITE_DOWNLOAD_AND_VERIFICATION_OK. Письмо «Резервная копия готова» подтверждает серверный этап; внешний этап проверять по журналу Mac.

## Операционные команды

На VPS:

```bash
systemctl list-timers --all after-login-backup.timer --no-pager
journalctl -u after-login-backup.service -n 30 --no-pager
df -h /
```

Ручное создание с ротацией: `systemctl start after-login-backup.service`. Не запускать параллельно скачиванию: общий flock предотвращает конфликт.

На Mac:

```bash
tail -n 15 ~/AfterLoginBackups/download.log
tail -n 15 ~/AfterLoginBackups/download-error.log
launchctl kickstart gui/$(id -u)/pro.milenin.after-login-backup
```

Без -k, чтобы не прерывать текущую загрузку. Повторная проверка выбранной копии:

```bash
python3 ~/AfterLoginBackups/verify-backup.py /полный/путь/к/папке-копии ~/AfterLoginBackups/private.pem
```

Клиент продолжает файл со смещения после обрыва и сверяет хеш. Незавершённые копии прошлых дат могут потребовать ручной очистки после анализа ошибки; автоматически они не удаляются.

## Порядок восстановления

1. Выбрать доверенную копию нужной даты и проверить её штатным verifier с соответствующим private.pem. Он проверяет и удаляет временные данные, не устанавливает сайт.
2. Подготовить отдельный закрытый тестовый сервер и рабочую копию данных; проверять HMAC до самостоятельной расшифровки/извлечения. Извлекать архив в изолированный каталог с контролем путей и symlink, не поверх production.
3. Восстановить Ghost MySQL и SQLite, content и фактический код Гостиной. Версии брать из manifest/inspect, compose и паспорта. Не заменять установленную локальную правку слепым git pull.
4. Проверить конфигурацию, зависимости, права, Nginx/TLS. Старые пользовательские сессии не переносить. После инцидента заменить секреты и отозвать восстановленные старые Admin keys до публичного запуска; не выпускать уязвимую версию Ghost в Интернет.
5. Проверить старт, статьи RU/EN, изображения, поиск, вход/почту Гостиной, подписку, webhooks. Только после успешной изолированной проверки планировать переключение DNS/production.
6. Переустановить расписания копий, restricted export и контроль релизов из Git; проверить контроль изменений и принять baseline только после проверки новой установки.

Этот порядок задаёт план восстановления; конкретные команды миграции подбирать по выбранной копии и новому серверу. Старый rollback.sh на Ghost 5.130.6 возвращает уязвимую версию и старые ключи: он не является безопасным постоянным восстановлением.

Код в scripts/: after-login-backup.py, after-login-backup-daily.py, after-login-backup-export.py, after-login-backup-download.py, after-login-backup-verify.py.

На VPS последняя проверка показала 2,9 GB свободно. Сохраняется одна актуальная завершённая копия; перед созданием проверяется место. Увеличение объёма media потребует пересмотра диска/хранения. Копии на Mac за пропущенные дни не появятся задним числом после серверной ротации.

Настройка согласованной защиты и обслуживания выполнена; обещание абсолютной безопасности не даётся. Причина изменения темы обоснована логами и известной уязвимостью; расследование полного ущерба остаётся открытым.
